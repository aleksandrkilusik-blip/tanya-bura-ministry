## Стан

Код підготовлений і локально перевірений. OAuth, ключі та тригер ще не активовані. Жоден лист не передано в OpenAI або GitHub. Сайт не змінювався.
Поточний main містить п’ять листів: листопадовий прибрали комітом 206cc68. Автоматизація зберігає поточний каталог.

## Перед підключенням

1. Gmail: потрібне окреме актуальне погодження на `gmail.readonly`. Google дозволяє читання всієї скриньки, а фільтрацію забезпечує код. Скрипт не надсилає, не позначає прочитаними, не переміщує і не видаляє листів. Додаткові scopes: зовнішні HTTP-запити та керування власним часовим тригером. Cru може вимагати погодження адміністратора.
2. GitHub: створити fine-grained PAT лише після погодження. Доступ виключно до `tanya-bura-ministry`: Contents — Read and write, Pull requests — Read and write, Metadata — Read. Рекомендований строк 90 днів. Без доступу до workflows чи інших репозиторіїв. PAT технічно дозволяє ширші зміни, ніж робить скрипт; код має дозволений перелік операцій і не оновлює main. Гілка main зараз не захищена правилами. Для захисту від дій поза цим кодом потрібне окреме налаштування ruleset.
3. Публічні чернетки: репозиторій публічний. Текст і фото будуть видимі на GitHub ще до Merge. Позначка Draft не робить PR приватним. Якщо потрібна конфіденційна чернетка, цей сценарій не слід активувати: спочатку потрібен приватний проміжний етап.
4. OpenAI API: перед створенням ключа й оплатою погодити окремий бюджет. ChatGPT-підписка не оплачує API. Модель указується вручну після вибору та перевірки її доступності і підтримки Responses + Structured Outputs. Скрипт передає OpenAI лише текст потрібного листа; фото не передає. `store:false` вимикає збереження Response, але не є обіцянкою повної відсутності зберігання даних провайдером.
5. Ключі вводити особисто в Project Settings → Script Properties. Не надсилати їх у чат, не записувати в код, файли, журнали або PR. Не надавати стороннім редакторський доступ до Apps Script: редактор може прочитати Script Properties.

## Установлення

1. У проєкті Apps Script вставити Code.gs у файл коду.
2. У Project Settings увімкнути показ appsscript.json і вставити наданий manifest. Він підключає Gmail API v1 із правом лише читання. Для стандартного Cloud-проєкту Gmail API може потребувати окремого ввімкнення.
3. Додати `START_AFTER_MS` — Unix час активації в мілісекундах, наприклад обчислений `Date.now()`. Це захищає від автоматичного імпорту архіву. Для перевірки реального нового листа дата повинна передувати його надходженню.
4. Після погодження OAuth запустити `checkInbox`. Він виводить тільки кількість кандидатів і не надсилає вміст стороннім сервісам. Не починає автоматизацію.
5. Після окремих погоджень додати `GITHUB_TOKEN`, `OPENAI_API_KEY`, `OPENAI_MODEL`. Потім `PUBLIC_DRAFTS_APPROVED=true`, `OPENAI_APPROVED=true`, `ENABLED=true`.
6. Провести погоджений тестовий запуск `pollTanyaLetters` на новому тестовому листі від Тетяни. Перевірити реальний Draft PR, обидві мови, фото, картку і повторний запуск без дубліката. Не Merge тестовий лист.
7. Лише після успішного тесту запустити `installHourlyTrigger`. Скрипт перевірятиме пошту щогодини, поки доступи й квоти чинні. Службовий комп’ютер може бути вимкнений.

## Формат листа від Тетяни

Від: tetiana.bura@cru.org
Кому: oleksandr.kyliushyk@cru.org
Тема — точно: Молитовний лист
Мітка в Gmail Олександра: PRAYER-LETTER (поставити вручну або наявним Gmail-фільтром; скрипт її не додає).

Текст листа:

    Місяць: 2026-09

    Дорогі друзі!
    [Новини служіння українською, історії та молитовні потреби.]

Вкласти 1–12 фото JPEG/PNG/WebP, до 5 МіБ кожне, разом до 18 МіБ. Зображення HEIC, SVG, PDF не підтримуються. Потрібна текстова MIME-версія листа — звичайний Gmail її додає. До 30 000 символів. Фото будуть галереєю після основного тексту: розташування за історіями можна відредагувати в PR. Скрипт не вигадує підписів до фото.

Тема `Re: Молитовний лист` та інші варіації не приймаються. Перевіряється From кожного повідомлення, не лише пошук чи ціла розмова. Це не криптографічна перевірка автора: застосовуються також звичайні засоби захисту Gmail від підробленої пошти.

## Ручне погодження

Відкрити Draft PR → звірити українську версію з оригіналом → перевірити переклад, місяць, фото та допустимість публікації персональних історій → переглянути локально/через наявний безпечний preview → Ready for review → вручну Merge.

Автоматизація не має Merge API, не змінює main, не запускає автозлиття. GitHub Pages опублікує результат після ручного злиття за чинним налаштуванням Pages. Новий випуск оновлює лише `letters/YYYY-MM.html`, власні фото та `letters.js`; попередні сторінки не переписуються.

## Витрати, помилки, пауза

- Apps Script і GitHub Pages працюють у межах їхніх безплатних квот; платний сервер не потрібен. OpenAI API оплачується окремо.
- Максимум 3 AI-спроби на календарний місяць UTC, максимум 10 000 вихідних токенів на спробу. Це обмеження кількості, а не гарантований грошовий бюджет. Навіть невизначені/невдалі спроби зараховуються.
- Один лист на запуск. Поки є відкритий автоматичний newsletter PR, наступний лист зупиняється для ручної перевірки. Існуючий випуск того самого місяця не переписується.
- Після помилки записується `ERROR_<reference>` і повторного AI-запиту для цього листа не буде. Перевірити виконання, провайдерські квоти та draft-гілки. Усунути причину й лише потім вручну видалити відповідну ERROR-властивість. Не очищати `AI_ATTEMPTS_*` для обходу ліміту.
- DONE-властивості й стабільні draft-гілки захищають від дублікатів. Закритий без Merge PR не створюється повторно автоматично.
- `pauseAutomation` або `ENABLED=false` припиняє обробку. Наявні PR зберігаються.
- Не видаляти START_AFTER_MS/DONE без розуміння наслідків. Старі листи не імпортуються автоматично.
